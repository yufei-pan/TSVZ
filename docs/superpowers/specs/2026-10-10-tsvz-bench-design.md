# TSVZ implementation benchmark (`tsvzbench.py`)

## Intent

A standardized benchmark that compares the performance and resource footprint
of implementations of tsvz-spec-v1, in any language, side by side on one
machine. It is used for local A/B comparisons: an implementation against the
reference, two versions of one implementation, or a candidate release against
the last one.

"Standardized" means fixed workloads on fixed, generated inputs, so numbers
from different implementations and different runs on one machine are
comparable. It is not a published leaderboard and not a conformance suite; its
correctness gate only makes sure a fast result did the work.

The existing `benchTSVZ.py` stays: it is the in-process `TSVZed` throughput
benchmark of the Python implementation. `tsvzbench.py` treats every
implementation, the Python reference included, as a black box.

### Decisions taken during design

| Question | Decision |
|---|---|
| Implementations compared | Any language, black box: only the spec's §20 command line and §21 handler socket are used |
| Use of results | Local A/B: a side-by-side table on the terminal; `--json` raw samples are secondary |
| Workload families | `cold` one-shot replay, `bulk` stdin batches, `perop` single operations (CLI and handler), `maint` scrub/clear plus format features |
| Approach | One stdlib-only script with built-in suites (not a declarative suite file, not a `hyperfine` wrapper) |
| Inputs | Generated by the harness, deterministic from a seed, byte-identical for every implementation |
| Correctness | A gate on every (workload, implementation): output and on-disk post-state checked against the harness's own replay model |
| Resource measurement | `os.wait4` on each child: wall, user/sys CPU, peak RSS, block I/O; `/proc` for a handler's RSS after load |
| Page cache | Warm: one untimed warm-up run first; dropping caches is out of scope |
| Fairness | Implementation order rotates on every repetition; medians with MAD spread |
| Baseline | The first `--impl`; every other implementation gets a ratio against it |
| Name and place | `TSVZ/tsvzbench.py`, beside `benchTSVZ.py`, not shipped in the wheel |

## 1. Invocation and implementation contract

```
python3 tsvzbench.py --impl NAME=COMMAND [--impl NAME=COMMAND ...]
                     [--suite smoke|quick|standard|large] [--only FAMILY[,FAMILY...]]
                     [--repeat N] [--timeout SECONDS] [--seed N]
                     [--work-dir DIR] [--keep] [--json PATH] [-h] [-V]
```

1.1 **`--impl NAME=COMMAND`**, repeatable, at least one. `NAME` matches
`[A-Za-z0-9_.-]+` and is unique. `COMMAND` is split with `shlex.split`; the
harness runs `COMMAND + ['--format', 'records', '-q', OPERATION, STORE, ARG...]`,
the canonical form of §20.1. `--format` and `-q` are options every conformant tool
accepts (§20.7.1). Generated keys and values never begin with `-`, so no `--`
separator is needed. The first `--impl` is the **baseline**.

1.2 **Capability probe**, once per implementation before any workload:

- `COMMAND -V` must exit 0. The first line of its standard output is recorded as
  the version string. An implementation that fails this is reported and skipped
  entirely; the harness exits 1 at the end.
- `COMMAND serve STORE` on a scratch store: the handler counts as supported when
  the pointer file `STORE.serve` appears within 10 s, is valid (§21.2: first line
  `tsvz-handler<TAB>1`, an `address` of `unix:PATH`) and a `len` request over its
  socket returns `#0`. The probe handler is then stopped (§6.3). An exit status 1
  (§20.2.6), a timeout or an invalid pointer marks the handler unsupported, and
  every handler workload shows `n/a` for that implementation.

1.3 **Environment.** Children inherit the harness's environment unchanged
(Python bytecode caches and the like are each implementation's business). Each
child gets its own session (`start_new_session=True`) so a timeout can kill its
whole process group.

1.4 **Isolation.** Each measured run works on a fresh copy of its fixture in
`WORK/impl/NAME/`, made outside the timed region and removed after the run
(§6.4). CLI workloads use store paths that never have a pointer file, so an
implementation's §20.8 forwarding cannot turn a direct measurement into a
handler one.

1.5 **Suites** fix every size and count. `--repeat` and `--timeout` override the
suite's values; `--only` selects families (`cold`, `bulk`, `perop`, `maint`).

| | smoke | quick | standard (default) | large |
|---|---|---|---|---|
| Sizes (rows) | 100 | 1k, 10k | 10k, 100k, 1M | 10k, 100k, 1M, 10M |
| Mid size | 100 | 10k | 100k | 1M |
| M, CLI single-op calls per op | 3 | 20 | 30 | 30 |
| Socket requests per op, sequential | 100 | 2,000 | 10,000 | 10,000 |
| `--sync` requests | 10 | 200 | 1,000 | 1,000 |
| Concurrent client counts | 1, 4 | 1, 4 | 1, 4, 16 | 1, 4, 16 |
| Requests per concurrent client | 50 | 1,000 | 5,000 | 5,000 |
| Timed repetitions R | 1 | 3 | 5 | 3 |
| Timeout per run | 30 s | 60 s | 300 s | 1800 s |
| Rough time, reference impl | seconds | ~1 min | ~5 min | 20+ min |

`smoke` exists to check a setup (and to test the harness) before a long run.

1.6 **Conventions.** One file, standard library only, Python ≥ 3.8, POSIX only.
`version = '1.0'` and `__version__ = version` near the top; `-V` prints it. The
harness never imports `TSVZ`: it must stay neutral between implementations.

## 2. Replay model, fixtures and the correctness gate

### 2.1 The replay model

2.1.1 The harness contains a small replay model that applies raw lines one at a
time following §7, for the strict TSVZ variant (TAB delimiter, version 1):

- framing: split on `\n`, strip one `\r` before it, discard bytes after the last
  `\n` (§4);
- classification: the reserved pattern `#_[A-Za-z0-9_-]+_#`, case-insensitive
  (§12.2); comments (§11); unrecognized markers, advisory markers
  (`#_rotate_#`, `#_write_ack_#`) and `#_checksum_<algo>_#` lines are inert;
- the stateful markers `#_version_#` (only `1` occurs), `#_defaults_#`,
  `#_strip_trailing_whites_#`, `#_fill_empty_with_default_#`,
  `#_return_defaults_when_missing_#`, including the empty-value reset (§12.1);
- tombstones decided on the raw row (§9), empty keys ignored (§8.4), trailing
  space/tab stripping (§10), §13 token decoding with unknown tokens passed
  through;
- last-wins in an ordered map whose delete removes the key's position, as
  Appendix B's `store.delete` does: a key deleted and then written again moves to
  the end. (§3.4's "first appearance" can be read otherwise; the reference
  implementation agrees with Appendix B, and the model follows both.)
- §14 resolution: each live row keeps the defaults in force at its position; a
  present-empty cell takes the default when fill-empty was on at that row.

2.1.2 **Store assembly** for reading files back (§17): the unnumbered file is
part 0, numbered parts follow by hexadecimal ordinal ascending, `.rotated` parts
are skipped, `.gz` parts are decompressed, and the parts are replayed as one
concatenation.

2.1.3 The **resolved row** of a live key is its key followed by
`max(written width, width of its bound defaults)` resolved cells, with trailing
empty cells removed. This trimmed form is what the gate compares (§2.3).

2.1.4 The model covers only what fixtures and workloads produce. It does not
verify checksums. It is checked against the reference implementation by the
harness's tests (§7.3).

### 2.2 Fixtures

2.2.1 Fixtures are generated deterministically from `random.Random(seed)`
(`--seed`, default 1), as strict `.tsvz` files. They are cached in
`WORK/fixtures/` under a name made of shape, rows, seed and `GENERATOR_VERSION`
(an integer constant bumped whenever generation changes). The expected state of
a fixture is computed by replaying **the bytes it wrote** through the model, so
expectation and file cannot drift apart.

2.2.2 Common row form: keys are 12 random characters from `[a-z0-9]` (unsorted,
unique by construction); values are 5 columns of 8–16 random characters from
`[A-Za-z0-9]`; about 70 bytes per row. Every fixture starts with a header comment
line `#key<TAB>c1<TAB>…<TAB>c5`.

2.2.3 Shapes, N = the fixture's live rows:

| Shape | Contents | Stresses |
|---|---|---|
| `plain` | N rows, one per key | baseline replay |
| `churn` | about 4N data lines with exactly N live keys at the end: overwrites, tombstones (≥ 20% of data lines), and keys written again after their tombstone | last-wins cost vs. live size; scrub input |
| `escaped` | as `plain`, with ~30% of cells holding a TAB (`<sep>`), a line feed (`<LF>`), a `<` (`<lt>`), a literal `<sep>` text (`<lt>sep>`), or non-ASCII text (Latin-1 range, CJK, emoji); ~2% of keys start with `#` (`<#>`); `#` also appears mid-field | §13 decoding |
| `markers` | `#_version_#` `1`, `#_defaults_#` with 5 values, `#_fill_empty_with_default_#` `true`; rows of random width 1–5 value columns with some present-empty cells and some trailing spaces; at the halfway line a second `#_defaults_#` with different values; for the last quarter `#_strip_trailing_whites_#` `false`; some early keys rewritten after the defaults change, others left bound to the first defaults | §14 resolution; §19.4 snapshot fidelity |
| `checksum` | as `plain`, with `#_checksum_crc32_#` every 1,000 lines and `#_checksum_sha256_#` every 1,500 lines, the first of each empty (arming), the rest carrying the correct lowercase hex digest of their segment (§15.4); crc32 is 8 zero-padded hex digits | integrity overhead; `verify` |
| `gz` | `plain` written as `STORE.tsvz.gz` | decompression |
| `multipart` | `plain` rows split across the unnumbered part 0 and 7 numbered parts with 32-hex-digit ordinals (UUIDv7-style, §17.6) whose lexical order differs from numeric order where possible; plus one `.rotated` part holding rows that must not appear | §17 assembly |

2.2.4 **Bulk inputs** are generated alongside: `bulk-new-N` (N `plain`-form
records with keys not in any fixture), `bulk-add-mid` (mid/100 new records),
`bulk-del-mid` (10% of the mid `plain` keys, one per line, chosen at random).

### 2.3 The gate

2.3.1 Each (workload, implementation) gets one gate result, from its warm-up run
(§4.2):

| Mark | Meaning |
|---|---|
| `✓` | output, exit status and post-state as expected |
| `✗` | wrong output or wrong post-state; the detail names the first difference |
| `! N` | unexpected exit status N |
| `⏱` | timed out |
| `n/a` | not run: handler unsupported, or the family was not selected |
| `refused` | an allowed refusal (only `scrub` of `multipart`, §3.4) |

2.3.2 **Comparing output.** Each output line is split on TAB and each field is
§13-decoded; the row is the decoded key plus its value cells with trailing empty
cells removed. Output rows are compared in order with the model's resolved rows
(§2.1.3). This accepts the padding §3.6 allows (`b⇥3⇥` equals `b⇥3`) but not a
row that omits a resolved default value. `len` output must be the exact integer.

2.3.3 **Comparing post-state.** After a mutating run the model reads the files the
implementation left (§2.1.2) and compares the resulting store, order included,
with the expected one. The bytes on disk are checked, not the implementation's
own report of them.

2.3.4 A gated failure still shows its timing, dimmed, so a suspiciously fast cell
is visible as such. An optional feature (`gz`, `multipart`) failing with a
non-zero exit shows as `! 1 (unsupported?)`.

## 3. Workloads

Every CLI measurement is one child process. Its standard input, when it has one,
is a prepared file; its standard output and standard error go to files in the
work directory. Nothing is piped through the harness.

### 3.1 `cold`: one-shot replay

| Workload | Store | Expected |
|---|---|---|
| `startup` | none: `COMMAND -V` | exit 0 |
| `read` | `plain` at every size | all rows |
| `len` | `plain` at every size | N |
| `get` | `plain` at every size, one live key and one missing key | exit 3; the live row, then the missing key with the (empty) active defaults, §14.5 (`nope` and `nope⇥` are equal under §2.3.2) |
| `read` | `churn`, `escaped`, `markers`, `checksum`, `gz`, `multipart` at mid size | all rows |
| `verify` | `checksum` at mid size | exit 0, no output |

`startup` is the per-implementation process floor; its median is subtracted to
give the *net* time of every other CLI workload.

### 3.2 `bulk`: standard-input batches (§20.3)

| Workload | Store | Input | Post-state |
|---|---|---|---|
| `set - new` | none (created) | `bulk-new-N`, every size | N rows |
| `set - add` | `plain` mid | `bulk-add-mid` | fixture + 1% |
| `delete -` | `plain` mid | `bulk-del-mid` | fixture − 10% |

### 3.3 `perop`: single operations

3.3.1 **CLI, direct.** On a `plain` mid store: M calls `set STORE KEY V1…V5`
(existing keys, new values), then M calls `get STORE KEY` (live keys). Reported
per call: median and p95 latency, peak RSS. Gate: every `get` row, and the
post-state.

3.3.2 **CLI, through the handler.** The same calls while the implementation's
own `serve` runs on that store. If its tool does not forward (§20.8 is a MAY), the
numbers match 3.3.1, which is itself worth knowing. Each repetition starts and
stops its own handler on a fresh copy.

3.3.3 **Raw §21.** The harness's own client on one connection, against the
implementation's handler on a `plain` mid store:

- sequential `get` of random live keys, then sequential `set` (90% existing
  keys, 10% new), each the suite's sequential request count;
- `--sync set` (§21.5.2), the suite's `--sync` count;
- for each concurrent client count C: C client processes (`fork` where
  available), each on its own connection, a 50/50 `get`/`set` mix. Each client
  reads and writes only keys it owns, disjoint from every other client's, so its
  `get` answers follow from its own earlier writes (§21.8.3) and the post-state
  is deterministic whatever the interleaving. Clients start together on a pipe
  barrier.

Each repetition (the warm-up included) copies the fixture afresh, starts a new
handler, runs all of the loads above in order, and stops it.

Reported: p50/p95/p99 latency in µs per request and ops/s (total requests over the
span from the first start to the last end). Gate: every status line `#0`; `get`
responses compared with the expected rows after the timed loop; the post-state
after `stop`.

3.3.4 **Client ceiling.** The same sequential and concurrent loads against a
built-in dummy server, a forked process that answers `#0` to every request line.
Its row shows where the harness client, not the handler, is the limit.

3.3.5 **Handler footprint.** For each handler run: load time (spawn until the
first `len` answer), RSS after load (`VmRSS` from `/proc/PID/status`, where PID is
the pointer file's `pid`, so a wrapper command does not hide the real process),
and after `stop` the total CPU and peak RSS from `wait4` on the spawned child.

### 3.4 `maint`: compaction

| Workload | Store | Expected |
|---|---|---|
| `scrub churn` | `churn` mid | exit 0; same state; smaller file; sizes before/after reported |
| `scrub markers` | `markers` mid | exit 0; same state (§19.4 fidelity) |
| `clear` | `plain` mid | exit 0; empty store |
| `scrub multipart` | `multipart` mid | exit 0 with the same state → `✓`; exit 1 with every part byte-identical → `refused` (§20.2.1); anything else → `✗` |

## 4. Measurement

4.1 **One run.** The harness starts the child with `subprocess.Popen` and reaps
it with `os.wait4(pid, 0)` (never `Popen.wait`), then sets the `Popen`'s
`returncode` itself. From the rusage it records `ru_utime`, `ru_stime`,
`ru_maxrss` (KiB on Linux, bytes on macOS; stored in bytes), `ru_inblock`,
`ru_oublock`, `ru_nvcsw`, `ru_nivcsw`. Wall time is `time.perf_counter()` from just
before `Popen` to just after `wait4`. Store growth is the change in the summed
sizes of the store's parts. On timeout the harness kills the child's process
group (SIGKILL) and records `⏱`.

4.2 **Repetitions.** For each (workload, implementation): one untimed warm-up run,
which is the run the gate checks, then R timed runs. A timed run only has to repeat
the warm-up's exit status; a different one is flagged in the cell. Repetitions are
interleaved across implementations, and the order rotates each repetition
(repetition r runs implementation `(i + r) mod n` in slot i).

4.3 **Statistics.** Reported values are medians; the spread is the median
absolute deviation as a percentage of the median. Socket workloads report
percentiles over all per-request timings of all timed repetitions.

4.4 **Derived figures.**

- *net wall* = wall − the implementation's median `startup` wall;
- *rows/s* = rows / net wall for `cold` and `bulk` (shown as `—` when net wall is
  not positive);
- *memory per live row* = (peak RSS at the largest size − at the smallest) /
  (difference in rows), for `read` and for `len` on `plain`;
- *disk bytes per record* = store size / N for `set - new` at the largest size.

## 5. Output

5.1 **Header.** Harness version, date, host name, CPU model, logical CPUs, kernel,
Python version of the harness, file system type of the work directory, the note
"warm page cache", seed, suite, and for each implementation its name, command,
version string and handler support.

5.2 **Tables**, one per family. Rows are workloads with their size; for each
implementation the columns are median wall (and net wall for CLI workloads),
spread, CPU (user + sys), peak RSS and the gate mark; every implementation after
the first also gets a `×ratio` of its median wall to the baseline's. Socket rows
show p50/p95/p99 and ops/s instead. The harness's own table formatter fits the
terminal width and uses colour only when standard output is a terminal.

5.3 **Footprint block**: memory per live row, disk bytes per record, handler RSS
after load and load time, for each implementation.

5.4 **Summary**: for each implementation, the geometric mean of its wall ratios
against the baseline per family, and the counts of `✗`, `!` and `⏱`. Below it,
for every failed cell, the last 5 lines of the run's standard error.

5.5 **`--json PATH`** writes every raw sample:

```json
{"schema": 1,
 "harness": {"version": "1.0", "suite": "standard", "seed": 1, "started": "…"},
 "env": {"host": "…", "cpu": "…", "cpus": 32, "kernel": "…", "python": "…", "fs": "…"},
 "impls": [{"name": "ref", "command": "python3 TSVZ.py", "version": "…", "handler": true}],
 "results": [{"family": "cold", "workload": "read", "shape": "plain", "rows": 100000,
              "impl": "ref", "gate": {"mark": "✓", "detail": ""},
              "samples": [{"wall": 0.0, "utime": 0.0, "stime": 0.0, "maxrss": 0,
                           "inblock": 0, "oublock": 0, "nvcsw": 0, "nivcsw": 0,
                           "exit": 0, "store_bytes": 0}],
              "latency": null}]}
```

`latency`, on socket rows, is `{"p50_us", "p95_us", "p99_us", "ops_s", "requests"}`.

## 6. Error handling

6.1 One failure never aborts the run: a crash, unexpected exit or timeout marks
the cell and the harness moves on. Each failed run's standard error is kept in the
work directory.

6.2 **Exit status of the harness**: 0 when every cell is `✓`, `n/a` or `refused`;
1 when any cell is `✗`, `!` or `⏱`, or an implementation failed the `-V` probe;
2 for a usage error; 130 after Ctrl-C.

6.3 **Handlers never outlive the harness.** Stopping one means sending `stop` over
§21, waiting up to 10 s for the spawned child to exit, then SIGTERM to its
process group, then after 5 s SIGKILL. The same cleanup runs for every live
handler from an `atexit` hook and on SIGINT/SIGTERM. Ctrl-C also prints the
results collected so far.

6.4 **Work directory.** The default is a fresh temporary directory, removed at
exit. `--work-dir DIR` uses DIR, and its `fixtures/` cache survives between runs.
Per-run store copies are removed after each run; `--keep` keeps the work
directory with the last copy of each (workload, implementation) and all standard
error logs.

6.5 **Preflight.** Before running, the harness estimates the space the suite needs
(fixtures, bulk inputs, and the largest concurrent per-run copy) and checks it
against `os.statvfs` of the work directory; when it does not fit it exits 1 with
the estimate and the free space.

6.6 **Platforms.** Linux is primary. On macOS everything runs except the handler's
RSS after load, shown `n/a` (no `/proc`). Without `os.wait4` or `AF_UNIX`
(Windows) the harness exits 1 at start with a message.

## 7. Testing

`tsvzbench_test.py`, plain pytest `test_*` functions, beside the harness.

7.1 **Model.** §13 round trips including `<lt>sep>`; the tombstone and empty-key
rules; last-wins with the delete-moves-to-end order; forward-bound defaults and
fill-empty; strip toggling; the spec's Appendix C worked example as a fixed
expected state.

7.2 **Generator.** The same seed and shape give byte-identical files; each shape's
fixture has the stated properties (N live keys, `churn`'s tombstone share,
`checksum` digests correct by an independent recomputation, `multipart` ordinals
out of lexical order).

7.3 **Cross-check with the reference.** For every shape at 1,000 rows, the
normalized `python3 TSVZ.py --format records read` output equals the model's
expected rows. A disagreement is investigated before either side is changed: the
reference may be the one that is wrong.

7.4 **Gate negatives.** Fake implementations written by the test as small Python
scripts, each run through the real harness path: one drops a row (`✗`), one omits
a resolved default (`✗`), one exits 1 (`! 1`), one sleeps past the timeout (`⏱`),
one writes a corrupted record on `set -` (`✗` post-state), one refuses
`scrub` of `multipart` without touching it (`refused`).

7.5 **§21 client** against the built-in dummy server: framing, status lines,
diagnostic lines (`#!`), and bulk `set -` termination.

7.6 **End to end.** `--suite smoke` against `--impl ref='python3 TSVZ.py'`
completes with every cell `✓` or `n/a`/`refused` as allowed, exit status 0, and
a `--json` file that parses with `"schema": 1`.

## 8. Packaging and documentation

- `tsvzbench.py` and `tsvzbench_test.py` are not added to `setup.py`'s
  `py_modules`; like `benchTSVZ.py`, they are development tools, not part of the
  wheel.
- `TSVZ/README.md` gains a short "Benchmarking implementations" section: the
  command line, the suites, how to read the table.
- The cas `CLAUDE.md` lists `TSVZ/tsvzbench.py` under Benchmarks.

## 9. Out of scope

- Comparing against a saved earlier run (`--baseline old.json`); the JSON format
  leaves room for it.
- Cold page cache runs (dropping caches).
- Loose variants and the CSVZ, NSVZ and PSVZ delimiters; only strict TSVZ is
  generated.
- Compression codecs other than gzip.
- Conformance testing beyond the gate; a fast tool is not certified correct by a
  `✓`.
- Linking the benchmark from the tsvz.org implementations page.
- Non-local (TCP) handler access.
